맵 제작 분석: MCP 방식 vs 파이썬 방식 (맵 3종 전체)

작성 시작: 2026-11-03 근거: 당시 작업 대화 기록 파일에서 직접 확인한 값만 적었고, 추정은 "추정"이라고 표시했다.

용어 풀이 (개발을 몰라도 읽을 수 있게)

  • 그레이박스: 회색 상자만으로 지형을 대충 세워서 동선과 크기감을 확인하는 단계.
  • MCP 방식: AI가 에디터에 "큐브 하나 놓아줘" 같은 지시를 하나씩 보내서 만드는 방식. 사람이 에디터를 조작하는 것과 비슷하다.
  • 파이썬 방식: 작은 프로그램(스크립트) 하나를 에디터에 보내서 한 번에 만드는 방식.
  • 좌표표: "어떤 모양을 어디에 얼마 크기로 놓을지"를 숫자로 적은 설계도. 두 방식이 같은 좌표표를 입력으로 썼다.
  • 액터: 에디터 맵 안에 놓이는 물체 하나하나(상자, 기둥, 보스, 시작점 등).
  • 훅: 특정 순간에 자동으로 실행되도록 걸어 둔 규칙.
  • PIE: 에디터 안에서 게임을 실제로 실행해서 걸어 보는 테스트.
  • 토큰: AI가 읽고 쓰는 글자의 단위. 많이 쓸수록 시간과 비용이 든다.

한눈에 보기

세 개의 미니던전(결투 회랑, 요새 돌파, 폐허 성곽길)을 각각 MCP 방식과 파이썬 방식으로 만들어 비교했다. 아래는 이 문서 전체의 결론이다. 근거와 한계는 각 장에 있다.

  1. 시간은 세 맵 모두 파이썬이 짧았다. 파이썬은 0.9~3.8초, MCP는 결투 회랑 약 5분(초기 방식), 요새 돌파 7~11초, 폐허 성곽길 약 6초였다. 다만 MCP를 묶음 호출로 개선한 뒤에는 격차가 수백 배에서 2~6배로 줄었다.
  2. 토큰(AI가 쓴 글자량)은 맵마다 달랐다. 결투 회랑에서는 파이썬이 MCP의 약 5분의 1이었다. 그러나 요새 돌파와 폐허 성곽길 세션에서는 파이썬 단계가 약 8.2만, MCP 단계가 약 6.6만으로 오히려 파이썬 쪽이 많았다. 파이썬 단계에 좌표표 설계(약 5.2만)가 들어 있었기 때문이다. "파이썬이 토큰도 적다"는 결투 회랑에서만 확인되고, 이후 세션에서는 조건이 달라 그대로 말할 수 없다.
  3. 가장 큰 병목은 방식마다 달랐다. MCP는 새 액터 저장 문제와 시작점이 원점으로 돌아가는 문제에 약 15분을 썼다. 파이썬은 에디터 연산이 거의 병목이 아니었고, 화면 캡처 설정(약 7분)과 이전 맵 삭제 권한 대기가 시간을 잡았다. 공통 병목은 좌표표 설계와 에디터 연결(약 17분)이었다.
  4. 가장 믿을 만한 검증은 "저장 후 다시 열어 숫자로 대조"였다. 이 방법으로 저장 누락, 저장 파일 부족, 시작점 문제를 잡았다. 게임을 직접 실행해 보는 테스트(PIE)는 세 맵 모두 하지 않았다.
  5. AI가 기획서에 없는 것을 추가하거나 값을 바꾼 곳이 있다. 종탑 시계, 깃발, 이끼, 그리고 폐허 성곽길의 통로 바깥벽 높이를 5m에서 4.2m로 낮춘 것. 담당 기획자 확인이 필요하다 (4장).

1. 의존한 메모리

여기서 "메모리"는 두 가지를 구분해서 적는다. 하나는 AI가 세션을 시작할 때 불러오는 기억 파일이고, 다른 하나는 AI가 필요해서 직접 찾아 읽은 프로젝트 문서와 이전 작업물이다.

1-1. 결투 회랑 (1번 세션)

세션을 시작할 때 자동으로 불러온 것은 세 가지다.

  • 전역 설정 CLAUDE.md (말투, "큰 작업은 계획 먼저" 같은 작업 규칙)
  • 프로젝트 규칙 AGENTS.md (임시 스크립트를 저장소에 두지 않는다는 규칙이 여기 있다)
  • 기억 목록 MEMORY.md

작업을 시작하며(16:29) AI가 직접 읽은 것은 다음과 같다.

  • 기억 파일 project-minidungeon-m2-status.md: 미니던전 3종 중 무엇이 확정이고 임시인지 정리된 기억. 이걸로 결투 회랑이 "AI가 기획한 임시안"임을 알았다.
  • 문서 인덱스, 결투 회랑 기획서, 보스 전장 기획서(보스 아레나 모양 참고)
  • 에디터 작업 요령 문서 ag-editor-workflow/SKILL.md: 에디터 다루는 순서와 이 프로젝트에서 겪은 함정

이 세션에서는 기억 파일이 실제로 쓰였다. 읽은 기억 파일은 한 개다.

1-2. 요새 돌파, 폐허 성곽길 (2번 세션)

이 세션은 작업 폴더가 C:\Dev였고, 이 폴더는 프로젝트 폴더(C:\Dev\Ag)가 아니었다. 그 결과가 1번 세션과 다르다.

  • 기억 목록 MEMORY.md는 불러오지 않았다. 세션 기록에 지침 파일이 전역 CLAUDE.md 한 개뿐이다. 이 폴더용 기억 폴더는 비어 있었다.
  • 기억 파일은 하나도 읽지 않았다. project-minidungeon-m2-status.md도 읽지 않았다.
  • 프로젝트 규칙 AGENTS.md는 자동 불러오기가 아니라, 기획서 읽는 순간 훅(자동 실행 규칙)이 끼워 넣어 줬다.
  • 에디터 작업 요령 문서는 읽지 않았다.

대신 AI는 파일을 직접 뒤져서 필요한 것을 찾았다.

  • 시작 직후(05:13) 폴더를 훑어서 AG_personal 폴더를 발견하고, 그 안의 결투 회랑 layout.py, build_py.py 등 이전 작업물을 읽었다.
  • 요새 돌파와 폐허 성곽길 기획서를 읽었다 (05:16).
  • 기억 파일 대신 이전 세션의 작업물이 사실상 기억 역할을 했다. 첫 요청에서 "하나는 레벨 제작을 끝냈다"는 말만 듣고 AG_personal의 결과물을 보고 파이프라인을 파악해 "결투 회랑 방식을 그대로 재사용하면 된다"고 판단했다.

2. 결과물 검증 방법

검증은 "만든 결과가 의도대로인지 확인하는 방법"이다. 맵마다 어떤 방법을 썼고 무엇을 못 했는지 적는다.

2-1. 쓴 검증 방법 네 가지

  1. 눈으로 보기: 에디터 화면을 이미지로 찍어 AI가 직접 보고 판단한다. 위에서 내려다본 그림과 시작 지점에서 본 그림을 쓴다.
  2. 설계도와 대조: 만들어진 액터의 위치를 좌표표 숫자와 비교한다. 오차(cm)로 나온다.
  3. 저장 후 다시 열기: 맵을 저장한 뒤 디스크에서 새로 읽어서 값이 유지되는지 본다. 에디터 메모리 속 값은 믿지 않고 파일에서 읽는 것이 핵심이다.
  4. 시선 계산(광선 검사): 시작 지점에서 탑 꼭대기까지 보이지 않는 선을 쏴서 중간에 벽이 가리는지 계산한다. 기획서에 "시작 지점에서 탑이 보여야 한다"는 확인 항목이 있어서 썼다.

2-3. 검증으로 실제로 찾아낸 문제

검증이 가치가 있었다는 증거다.

  • 파이썬 맵의 보스, 시작점, 내비 영역 이동이 저장에서 빠졌다 (결투 회랑). 다시 열어 보고 발견했다.
  • 요새 돌파 MCP 맵이 저장 파일 수가 모자랐다 (98개 대 205개). 파일 수를 세어 비교해서 발견했다.
  • 시작점(PlayerStart)이 다시 열면 원점으로 돌아가는 현상 (요새 돌파 MCP 맵). 파일에는 정상 위치가 저장돼 있는데 불러오면 0이었다. 원인은 찾지 못했고, 지우고 새로 만드는 방식으로 피했다.
  • 폐허 성곽길의 종탑이 시작 지점에서 가려진다는 사실을 시선 계산으로 알았다. 이건 기획서가 "확인하고 높이를 조정"하라고 한 항목이다.
  • 화면 캡처가 처음에 저장되지 않았다. 에디터가 백그라운드 창이라 그림 그리기를 멈춘 것이 원인이었고, 그 설정을 잠시 끄고 찍은 뒤 원래대로 되돌렸다. 한 번은 카메라가 바닥만 찍어 쓸모없어서, 대신 시선 계산을 썼다.

2-4. 하지 않은 검증

  • 게임 실행(PIE): 세 맵 모두 안 했다. 점프 높이, 적의 시야, 경사로 오르내림은 확인되지 않았다.
  • 기획서의 시야 조건 중 일부: 결투 회랑의 난간 너머 엿보기, 기둥 뒤 가림 등은 확인하지 않았다.
  • 새 높이로 바꾼 폐허 성곽길의 종탑 시야와 12m 낙하 규칙.
  • 요새 돌파, 폐허 성곽길의 MCP 맵 화면 확인: 파이썬 맵과 숫자가 일치한다는 대조로 대신했다.
  • 시작점을 새로 만드는 코드가 들어간 MCP 빌드 스크립트를 처음부터 끝까지 다시 돌려 보지 않았다. 같은 동작을 직접 해서 확인한 데까지만 검증했다고 AI 스스로 기록해 두었다.

2-5. 기록상 서로 어긋나는 부분

AI의 최종 요약에는 "파이썬 맵과 MCP 맵을 대조했더니 색 머티리얼까지 전부 같다"는 말과 "보이는 차이로 파이썬 맵은 격자 무늬, MCP 맵은 기본 회색"이라는 말이 같이 있다. 두 설명이 한꺼번에 맞을 수 없다. 어느 쪽이 정확한지는 에디터에서 두 맵을 열어 확인해야 한다.

2-6. 정리

  • 가장 믿을 만한 검증은 "저장 후 디스크에서 다시 읽어 숫자로 대조"다. 이걸로 실제 문제 세 건을 잡았다.
  • 눈으로 보기는 모양을 확인하는 데는 좋지만 위치 오류를 못 잡았다.
  • MCP 맵을 파이썬 맵과 숫자로 대조한 덕에 MCP 맵의 품질도 보증할 수 있었다. 결투 회랑은 액터 구성이 달라 이 대조를 하지 못했다.

3. 병목: 시간이 실제로 많이 걸린 곳

병목은 "작업 전체에서 시간을 가장 많이 잡아먹은 구간"이다. 세션 기록의 시각표로 구간을 나눠서 적는다. 시각은 모두 기록에 남은 것이고, 구간 이름은 내가 붙였다.

주의: 이 25분에는 폐허 성곽길의 높이 재설계도 섞여 있다. 사용자가 "시작 위치가 높아야 한다"고 바꾼 요청을 같은 구간에 처리했고, 두 맵(파이썬, MCP)에 모두 반영했다. 재설계 시간을 따로 떼어 낼 수는 없다.

3-5. 읽는 법과 한계

  • 에디터가 실제로 연산한 시간은 매우 짧다 (파이썬 0.9초). 병목은 대부분 "AI가 생각하고 쓰는 시간", "문제를 찾고 우회하는 시간", "사람의 판단을 기다리는 시간"이었다.
  • 좌표표 설계는 두 방식이 공통으로 쓰는 일이지만, 파이썬을 먼저 하면 파이썬 쪽에 붙고 MCP를 먼저 하면 MCP 쪽에 붙는다. 결투 회랑은 MCP 쪽에 붙었고, 요새와 폐허는 파이썬 쪽에 붙었다 (2번 세션은 파이썬을 먼저 했다).
  • 그래서 두 세션 모두 "파이썬이 빨랐다"로 읽으면 안 된다. 공통 작업이 어느 쪽에 붙었는지 보고 읽어야 한다.
  • 시각표에서 "AI가 생각한 시간"과 "에디터가 일한 시간"을 정확히 나눌 수는 없다. 기록은 이벤트 사이의 간격만 남기 때문이다.
  • 2번 세션 끝의 43분 공백(06:05~06:48)은 사용자가 결과를 읽고 세션을 저장하기까지의 시간으로, 병목에 넣지 않았다.

4. 추론한 곳 (기록으로 확인되지 않아 AI가 짐작하거나 정한 부분)

"추론"은 기획서나 기록에 근거가 없어서 AI가 스스로 판단한 부분이다. AI가 직접 "가정", "확신 없음"이라고 적은 곳과, 기록을 보니 AI가 정한 곳을 나눠 적는다.

4-1. 결투 회랑

  • 바닥 높이를 0으로 가정했다.
  • 시작점(92)과 보스(100)의 높이는 짐작이다. 땅에 박히거나 떠 있을 수 있다.
  • 설계 문서는 +Y가 위쪽인데 언리얼 위에서 본 화면은 +Y가 아래쪽이다. 문서 좌표를 그대로 써서 기획서 도식과 위아래가 뒤집혀 보인다. 게임 플레이에는 영향이 없다.
  • 색 지정이 없어 전부 같은 회색으로 만들기로 했다.
  • 기획서의 치수를 상자 73개로 쪼개는 방식은 AI의 해석이다.

4-2. 요새 돌파, 폐허 성곽길

AI가 처음에 스스로 밝힌 것:

  • 기획서의 좌표와 치수를 그대로 쓰고, 랜드마크는 기획서 크기를 지키며 형태만 입힌다고 가정했다.
  • 결투 회랑의 맵이 두 개(LV_DuelCorridor, LV_DuelCorridor_Py)인데 어느 쪽이 정본인지 몰랐다. 실제로는 _Py 맵을 복제해서 바탕으로 썼다.
  • 맵 이름은 _Py 방식을 따랐고, 폐허 성곽길은 기획서의 가안 이름 LV_TempDungeon03을 썼다.

AI가 기획서에 없는 것을 직접 추가한 곳:

  • 사용자가 말한 "시계탑"을 폐허 성곽길의 종탑이라고 추정해서 그쪽에 시계를 달았다 (시각은 3시 정각, AI가 정함).
  • 요새 돌파의 탑에 모서리 기둥, 가로 띠, 좁은 창, 톱니 흉벽, 깃대와 빨간 깃발을 달았다.
  • 종 방의 기둥과 보, 구리색 종, 무너진 지붕 한쪽, 이끼 조각, 돌무더기를 추가했다.
  • 색 팔레트(돌, 이끼, 청동 등 9색)를 AI가 정했다.

AI가 기획서의 값을 바꾼 곳:

  • 폐허 성곽길의 통로 동쪽 바깥벽을 AI가 처음 정한 5m에서 4.2m로 낮췄다. 성벽 위 통로에서 종탑이 보이게 하려는 목적이었다. 이건 담당 기획자가 확인해야 한다.

사용자의 지시를 AI가 해석한 곳:

  • "난간이 작은 곳, 즉 시작 위치 자체가 높이가 높아야 한다"는 말을 "낮은 담으로 마당을 엿보는 자리를 시작부터 높은 지대로 올리는 것"으로 이해했다. AI가 자기 해석을 보고에 밝혔다.
  • 이 해석에 따라 시작 높이를 사용자에게 선택지(6m, 4.5m, 8m 이상)로 물었고, 사용자가 시작 6m와 "비탈길 6m에서 12m"를 골랐다.
  • 그 선택에서 파생된 변경(마당에서 통로로 올라오는 경사로를 20m로 늘림, 출구와 단 구역을 서쪽으로 약 4.5m 이동, 지대와 비탈길 밑 채움, 적 표식 높이 조정)은 AI가 정했다.

AI가 원인을 짐작했다가 바뀐 곳:

  • MCP 맵의 저장 파일이 모자라자 "저장이 덜 된 것 같아"라고 짐작했고, 파일 수를 세어 확인했다 (짐작이 확인으로 바뀐 사례).
  • 시작점이 원점으로 돌아가는 현상은 원인을 찾지 못했다. "지우고 새로 만들면 유지된다"는 우회만 확인했다.
  • 화면 캡처가 저장되지 않는 원인을 "백그라운드 창이라 그림 그리기를 멈춘 것"으로 짐작해 설정을 껐더니 해결됐다.

4-3. 이 분석 문서를 쓰면서 한 추정

  • 결투 회랑에서 좌표표 설계가 파이썬 쪽에 붙었다면 격차가 줄거나 뒤집혔을 것이라는 말은 시각표로 짐작한 것이다.
  • MCP 실행 시간의 이상치 두 건(186초, 256초)의 원인은 기록에 없다.

  • Blender: AI가 "형태를 더 다듬으려면 Blender로 모델링해서 가져올 수 있다"고 제안했지만, 사용자가 도형 조합으로 가자고 해서 쓰지 않았다.
  • Godot 연결 도구: 결투 회랑 세션에서 연결 충돌의 원인이어서 껐고 작업에는 쓰지 않았다.
  • 위키(knowledge-graph)와 이미지 생성 도구도 쓰지 않았다.

8-3. 기억과 대조

  • "파이썬이 시간이 적게 들었다": 세 맵 모두 기록으로 확인된다. 단 격차는 개선 전과 후가 크게 다르다.
  • "파이썬이 토큰도 적게 들었다": 결투 회랑에서만 분명하다. 나머지 두 맵에서는 설계 비용 때문에 합계가 더 많았고, 설계를 뺀 순수 제작 비용으로는 파이썬이 적었다.

9. 예상되는 한계점

  1. 사례가 3개뿐이고 반복 측정이 아니다. 시간 편차를 알 수 없다.
  2. 조건이 같지 않다. 결투 회랑은 MCP가 설계 비용을 떠안았고, 요새와 폐허는 파이썬이 떠안았다. MCP 방식은 도중에 개선되었다(묶음 호출).
  3. MCP 실행 시간의 이상치. 186초와 256초는 원인을 모른다. 재현 실험이 필요하다.
  4. 호출 횟수의 출처가 다르다. 결투 회랑은 실측이고 나머지 두 맵은 스크립트에서 계산한 값이다.
  5. 토큰에는 설명글이 포함된다. AI가 사람에게 쓴 보고도 들어 있어 순수 작업량이 아니다.
  6. 검증이 부분적이다. 게임 실행(PIE)을 안 했다. 시선 조건 일부와 새 높이에서의 종탑 시야는 확인되지 않았다. 폐허 성곽길의 12m 낙하 규칙은 사용자 결정이 필요하다.
  7. MCP와 파이썬 맵의 머티리얼 모순. 2번 세션 요약에 "전부 같다"와 "격자 무늬 대 기본 회색"이 같이 있다. 에디터에서 확인해야 한다.
  8. MCP 빌드의 일부 미검증. 시작점을 새로 만드는 코드가 들어간 빌드 스크립트를 처음부터 끝까지 다시 돌려 보지 않았다 (AI 스스로 기록).
  9. 세션 기록의 한계. 기록은 사건의 간격만 남겨서 "AI가 생각한 시간"과 "에디터가 일한 시간"을 정확히 나눌 수 없다.
  10. 기획서와 맵의 불일치. 폐허 성곽길 기획서는 옛 높이(시작 0m, 통로 3m)로 남아 있고 맵은 새 높이다. 기획서 수정은 승인 대기 상태다.
  11. 재현에는 조건이 필요하다. 에디터가 켜져 있어야 하고 8001 포트로 열려야 한다. 이전 맵의 정리와 삭제는 권한 설정에 막힐 수 있다.
