# 마일스톤1 구현 계획

마일스톤1 기획서를 어떻게 구현할지 정합니다. 기술 결정, 클래스 구조, 에셋 목록, 작업 순서를 이 문서 한 곳에 적습니다. 데이터가 어느 파일의 어느 필드에 있는지는 [데이터 위치표](<데이터 위치표.md>)에 따로 적습니다.

무엇을 만들지는 `Docs/Design`의 기획서를, 작업 방식은 [AI 워크플로우](<../AI 워크플로우.md>)를 따릅니다. 기간과 목표는 [마일스톤1 계획](<../Design/마일스톤1 계획.md>)을, 용어는 [용어집](<../용어집.md>)을 따릅니다.

## 범위와 완료 기준

- 기획서의 모든 항목을 구현합니다.
- 일정보다 완성도를 우선합니다. 일정 때문에 항목을 빼거나 완성도를 낮추지 않고, 필요하면 일정을 늘립니다.
- 각 단계는 아래를 모두 만족하면 끝납니다.
  1. 에디터 빌드가 오류 없이 성공합니다.
  2. 그 단계의 확인 항목을 PIE에서 기획서와 대조해 확인합니다.
  3. 자동 테스트가 있으면 모두 통과합니다.
  4. 새로 만든 데이터 필드를 [데이터 위치표](<데이터 위치표.md>)에 추가합니다.
  5. 코드를 push합니다.
- 모든 항목을 구현하고 단계별 확인을 마치면 QA에 넘깁니다.

## 기술 결정

### 기본 방침

| 항목 | 결정 | 이유 |
| - | - | - |
| 진행 방식 | 타이틀 화면 → 최소한의 전투가 되는 보스전 → 결과 UI를 먼저 잇고, 그 위에 기능을 채웁니다. | 마일스톤 목표 1을 일찍 확보하고, 늘 처음부터 끝까지 실행되는 상태를 유지합니다. |
| 새 에셋 위치 | 새로 만드는 에셋은 `/Game` 바로 아래 종류별 폴더에 둡니다('에셋 목록'). 템플릿 에셋은 원래 폴더(`Characters/Mannequins`, `LevelPrototyping`, `ThirdPerson`, `Variant_*`)에, Fab 에셋은 `Fab`에 둡니다. | 경로에 프로젝트 이름(`/Game/Ag`)이나 같은 단어(`/Game/Game`)가 겹치면 헷갈립니다. 템플릿·Fab 에셋은 각자의 폴더에 있어 구분됩니다. |
| Fab 모션 | 쓰는 시퀀스의 루트 모션 설정은 원본에서 켭니다. | 같은 모션을 두 벌 두지 않습니다. |
| 템플릿 코드·콘텐츠 | 새 코드는 Ag 접두사로 따로 만듭니다. LV_BossStage를 Lvl_Combat에서 복사한 뒤, 템플릿 코드(`Variant_*`, `AgCharacter`)와 템플릿 블루프린트(애니메이션·위젯 블루프린트 포함), 샘플 레벨 4개, 입력·AI 에셋을 지웁니다. 메시, 머티리얼, 텍스처, 애니메이션, 몽타주, 나이아가라, 컨트롤 릭 같은 리소스는 대역 에셋(NS_Damage, LevelPrototyping 폴더, MI_ThirdPersonColWay) 말고도 나중에 쓸 수 있어 남겨 둡니다. 패키징은 게임 맵 2개(`LV_FrontEnd`, `LV_BossStage`)만 쿡합니다. | LV_BossStage를 만들기 전에는 Lvl_Combat이 템플릿 에셋을 쓰므로 지울 수 없고, 그 뒤에는 비슷한 이름의 템플릿 클래스가 혼동을 줍니다. 템플릿 블루프린트와 그에 딸린 레벨·입력·AI 에셋은 템플릿 캐릭터용이라 쓰지 않고, 상당수는 부모 클래스(템플릿 코드)가 없어 쓸 수도 없습니다. 쿡할 맵을 정하지 않으면 프로젝트의 모든 맵을 쿡합니다. |
| 시간 처리 | 기획서의 시간 규칙이 애매하면(타이머와 모션 시간, 게임 시간과 실제 시간 등) 구현하기 쉬운 쪽으로 정하고 이 문서에 적습니다. | 기획 단계에서 정한 방침입니다. |
| 구조 선택 | 코드 구조는 AI가 작업하기 편한 쪽보다 엔진이 권장하는 쪽을 따릅니다. 엔진·프레임워크 기능이 기대대로 동작하지 않으면, 관계없는 클래스(PlayerController 등)에 우회 코드를 넣지 않고 그 기능의 설정과 확장 지점(에디터 설정, 위젯, CommonUI 하위 클래스 등)을 먼저 찾습니다. | 엔진 기능을 설계된 대로 써야 코드가 엔진의 동작과 어긋나지 않습니다. |
| 객체 수명 | `TStrongObjectPtr`와 `AddToRoot`를 쓰지 않습니다. 객체는 그것을 쓰는 액터나 컴포넌트가, 게임 전체가 쓰는 객체는 에셋 매니저가 UPROPERTY로 들고, 네이티브 클래스의 기본 객체(프로젝트 설정 포함)에는 값(수치, 열거형, 소프트 경로)만 둡니다. | 객체 수명을 GC가 관리합니다. 패키징 빌드에서는 네이티브 기본 객체를 GC가 따라가지 않으므로, 나중에 만들거나 읽은 객체를 가리키게 두면 안 됩니다. |

### 캐릭터와 GAS

| 항목 | 결정 | 이유 |
| - | - | - |
| ASC 위치 | 캐릭터에 둡니다. | 싱글플레이라 PlayerState에 둘 이유가 없습니다. |
| 어트리뷰트 | 세트 하나에 기획서 스탯을 기획서 이름 그대로 둡니다. HP, MaxHP, SP, MaxSP, MP, MaxMP, UP, MaxUP, PP, MaxPP, ATK, DEF, MOV. 보스가 쓰지 않는 SP·MP·UP는 0입니다. 기본값이 바뀌기 전에 범위(0 ~ 최대값)로 고정합니다. | 기획서, 데이터 위치표, 코드의 이름이 같아 대조하기 쉽습니다. 최대값에서 리젠이 더해져도 기본값이 넘치지 않아야 다음 감소가 바로 보입니다. |
| 행동 | 플레이어 행동(평타, 회피, 회피 반격, 가드·패리, 스킬, 궁극기, 처형, 달리기, 점프, 점프 공격)과 보스 패턴은 어빌리티로 만듭니다. | 행동, 쿨다운, 자원을 어빌리티·GameplayEffect·태그 한 방식으로 처리합니다. |
| 어빌리티 구조 | 어빌리티는 모두 `UAgGameplayAbility`를 바로 상속하고, 그 사이에 중간 클래스를 두지 않습니다. 여러 어빌리티가 함께 쓰는, 시간에 걸친 동작은 AbilityTask로 만듭니다(판정 구간이 있는 공격('공격 진행'), 피격 반응 모션과 쓰러진 뒤의 무적, 루트 모션 무시, 공격 중 이동, 컷신 재생). 한 번에 끝나는 조회(패턴 데이터 찾기, 첫 판정 구간 전의 이동 거리)는 함수로 둡니다. GAS가 정한 확장 지점(비용, 쿨다운(보스 패턴은 패턴별), 종료)과 여러 어빌리티가 같이 쓰는 생성자의 태그 설정은 `UAgGameplayAbility`에 둡니다. 태스크는 델리게이트로 알리기만 하고, 행동 중·후딜과 어빌리티를 끝낼지는 어빌리티가 정합니다. 캐릭터는 플레이가 끝날 때(EndPlay) 어빌리티를 모두 취소합니다. | 한 어빌리티의 흐름이 부모와 자식 파일로 나뉘지 않고, 부모가 다른 어빌리티끼리도 같은 동작을 나눠 쓸 수 있습니다(넉업과 A3 돌진의 루트 모션 무시). 태스크는 어빌리티가 끝나면 엔진이 함께 끝내므로, 켜 둔 상태를 되돌리는 코드가 그 기능 옆에 있습니다. ASC는 자기가 등록 해제될 때에야 어빌리티를 취소하는데, 그보다 먼저 메시가 등록 해제되며 몽타주를 끊으면 살아 있는 어빌리티가 그 콜백에서 메시를 바꿉니다(PIE 종료 때 처형 사망의 래그돌이 등록 해제 중인 메시에 물리 상태를 다시 만들어 엔진 ensure). |
| 상태 | 피격 반응, 그로기, 처형 피격, 페이즈 전환, 사망은 이벤트로 발동하는 어빌리티로 만들고, 상태 우선순위는 태그로 나타냅니다. 높은 상태는 낮은 상태를 취소하고, 낮은 상태는 높은 상태 중에 시작하지 못합니다. 4순위 피격 반응(넉업, 넉백, 가드 밀림, 가드 브레이크)의 어빌리티 태그는 한 부모 태그(`Ability.Reaction.HitReaction`) 아래에 두어, 높은 상태가 부모 태그 하나로 취소합니다. 어빌리티가 붙이는 상태 태그는, 어빌리티가 도는 내내 붙으면 ActivationOwnedTags에 두고, 일부 구간에만 붙으면(회피의 무적 구간, 가드 중 등) 태그 유지 태스크(`UAgAbilityTask_HoldTag`)로 붙입니다. | 행동과 같은 방식이라 규칙이 한곳에 모입니다. 두 방식 모두 어빌리티가 끝나면 엔진이 태그를 떼므로, 어빌리티마다 태그를 떼는 코드를 두지 않습니다. |
| 피격 처리 | 공격은 대미지 GameplayEffect를 적용하는 것으로 끝나고, 피격 처리는 그 GameplayEffect 안에서 이루어집니다. 피격 처리 순서와 대미지 계산식은 계산 클래스(`UAgDamageExecution`)가, 사망·그로기 판정은 어트리뷰트 세트의 GameplayEffect 실행 뒤 처리(`PostGameplayEffectExecute`)가, 결과에 따른 반응과 적중 후 처리는 GameplayEffect 컴포넌트(`UAgHitResultGameplayEffectComponent`)가 맡습니다. | GAS가 권장하는 구조입니다. 공격 방식(무기 스윕, 투사체, 착지 범위, 처형)마다 처리 함수를 부르지 않아도, 대미지 GameplayEffect만 적용하면 피격 처리가 빠짐없이 따라옵니다. |
| 쿨다운 | 쿨다운용 GameplayEffect로 처리합니다. 쿨다운, 리젠 대기, 패리 구간, 가드 시작 후 이동할 수 없는 시간은 시간과 태그를 적용할 때 정하는 GameplayEffect 하나를 같이 씁니다. 비용(SP·MP·UP)은 '자원 변화'를 따릅니다. | GAS 기본 방식입니다. 값이 캐릭터·공통 데이터에 있어 GameplayEffect 에셋에 따로 둘 데이터가 없습니다. |
| 자원 변화 | 자원이 바뀌는 일마다 그 규칙을 가진 GameplayEffect를 적용합니다. 행동 비용은 어빌리티의 비용 GameplayEffect(`CostGameplayEffectClass`)로 엔진이 커밋할 때 치르고, 줄이는 양은 비용 GameplayEffect의 계산 클래스가 어빌리티에서 읽습니다. 치를 수 있는지는 어빌리티가 플레이어 사양의 행동별 조건으로 확인합니다. MP·UP 충전과 극한 회피의 SP 반환은 얻는 양을 SetByCaller로 받는 자원 GameplayEffect로, PP 회복(그로기가 끝날 때, 페이즈 전환)은 PP를 최대로 덮어쓰는 GameplayEffect로, 패리로 공격자가 잃는 PP는 계산 클래스가 양을 정하는 GameplayEffect로 처리합니다. 극한 회피와 패리의 보상은 그 구간을 연 회피·가드 어빌리티가 그 이벤트를 받아 줍니다. | 양을 정하는 규칙이 GameplayEffect에 있어, 적용하는 쪽이 양을 계산하지 않습니다. 비용은 GAS가 정한 자리(비용 GameplayEffect)로 치릅니다. 보상을 구간을 연 어빌리티가 주면 극한 회피와 패리가 같은 방식이 됩니다. |
| 모션 캔슬 | 행동 어빌리티는 후딜 전까지 '행동 중' 태그를, 모션이 끝날 때까지 '행동 모션' 태그를 갖습니다. 후딜 시작은 '애니메이션과 이동'의 '모션을 따르는 구간'과 '기획서에 초로 적힌 구간'을 따릅니다. 새 행동은 '행동 중' 태그가 없을 때만 시작하고, 시작하면 진행 중인 행동을 취소합니다. 회피 후딜에 회피를 누르면 회피를 처음부터 다시 시작합니다. 이동 입력은 '행동 모션' 태그가 있는 동안 무시합니다. 플레이어 행동, 보스 패턴, 피격 반응, 그로기(처형 피격 포함), 페이즈 전환은 블렌드 아웃이 시작될 때가 아니라 모션이 끝날 때 끝납니다. 피격 반응에 이어지는 모션(넉업의 기상)은 앞 모션이 블렌드 아웃을 시작할 때 잇습니다. | 상태별 허용 입력 표를 그대로 옮길 수 있습니다. 이동만 후딜에도 막히므로 태그를 따로 둡니다. 블렌드 아웃은 모션 끝보다 먼저 시작해, 그때 끝내면 후딜과 피격 반응(기상 무적 포함)이 모션보다 짧아지고 그로기가 지속 시간보다 짧아지며, 페이즈 전환의 무적이 포효가 끝나기 전에 풀립니다. |
| 선입력 | 플레이어 캐릭터가 입력을 받을 때 '행동 중'이나 피격 반응 태그가 있으면, 그 입력 하나와 누른 시각(월드 시간)을 기억합니다. 점프 중의 평타 키는 점프 공격으로 허용되므로 기억하지 않습니다('점프 공격'). 입력은 그때도 그대로 처리하므로 허용되지 않은 행동은 시작하지 않고, 진행 중인 어빌리티가 받는 입력(패리 모션 중의 가드)은 그대로 받습니다. 두 태그가 풀리면 다음 프레임에 기억한 입력을 다시 처리하고, 기억하는 시간이 지났거나 가드 키를 뗐으면 버립니다. 가드 키를 누른 채 행동이 끝나 가드를 다시 시작할 때도 기억한 입력을 먼저 처리합니다. | 입력이 한 함수로 모이고 허용되는 순간이 태그 두 개로 드러나, 행동 어빌리티를 고치지 않아도 됩니다. 다음 프레임에 처리해야 같은 프레임에 이어지는 상태(평타의 후딜 표시, 행동을 끊은 피격 반응)가 반영됩니다. 월드 시간은 히트스톱 중에도 흐릅니다. |
| 리젠 | SP·PP 리젠은 GameplayEffect로 처리합니다. 리젠 대기는 태그를 주는 지속 GameplayEffect로, 자원이 줄 때마다 다시 적용해 처음부터 다시 셉니다. SP가 0이 될 때는 더 긴 대기용 GameplayEffect를 적용합니다. 회복은 주기 GameplayEffect로 하고, 대기 태그가 있는 동안에는 멈춥니다. SP는 평소용과 가드 중용 주기 GameplayEffect를 가드 태그 조건으로 바꿔 씁니다. 회복 GameplayEffect의 크기 계산 클래스(`UAgRegenCalculation`)가 주기마다 주인의 캐릭터 데이터에서 초당 회복량을 읽어 주기를 곱하고, 주기는 회복 GameplayEffect의 `Period`입니다. 캐릭터마다 거는 회복 GameplayEffect는 캐릭터 DataAsset의 목록(`RegenEffects`)에 두고, 캐릭터가 시작할 때 겁니다. 대기 시간은 캐릭터·공통 데이터에서 읽어 적용합니다. | 자원 변화를 모두 GameplayEffect로 처리하는 GAS 표준 방식입니다. 회복량을 GameplayEffect가 주기마다 읽으므로, 데이터 파일을 다시 읽어도 효과를 다시 걸 필요가 없습니다. GameplayEffect 타이머는 게임 시간으로 흘러, 히트스톱 중에도 리젠이 계속되는 기획서 규칙과 맞습니다. |

### 데이터

기획서의 데이터(수치, 설정, 쓰는 에셋)는 주인이 분명한 곳에 둡니다. 각 데이터의 위치는 [데이터 위치표](<데이터 위치표.md>)에 정리합니다.

| 항목 | 결정 | 이유 |
| - | - | - |
| 형식 | 기획서에 적힌 수치와 설정 가운데 기획자가 밸런싱하고 조절하는 값은 JSON 파일에 둡니다. 기획서에 없는 구현 값과 코드 연결(시작할 때 주는 어빌리티와 거는 리젠 GameplayEffect, 패턴을 실행하는 어빌리티와 쿨다운 태그, 코드가 읽는 본 이름)은 캐릭터 DataAsset에, 모든 캐릭터에 공통인 구현 값은 그 값을 쓰는 클래스(리젠 GameplayEffect의 주기, 사망 어빌리티의 래그돌 밀림 속도)에 둡니다. 몽타주처럼 Content의 에셋을 가리키는 참조는 DataAsset에 둡니다. 엔진 컴포넌트와 애님 노드의 설정(스프링 암과 카메라, 블렌드 노드의 블렌드 시간, 충돌 상자의 크기, 무기 컴포넌트의 메시와 붙이는 소켓)은 JSON에 두지 않고 그 블루프린트에 직접 적습니다. 데이터 하나는 이 가운데 한 곳에만 있습니다. | 작업은 AI가 하고 사람은 판단하고 리뷰합니다. JSON은 에디터 없이 읽고 고칠 수 있고, 바뀐 수치가 커밋 diff에 보이며, 두 사람이 같은 파일을 고쳐도 병합됩니다. 에셋 참조는 DataAsset에 있어야 에셋 이름을 바꾸거나 옮길 때 엔진이 따라 고치고, 패키징할 때 쿡에서 빠지지 않습니다. 엔진 설정을 JSON에 두면 코드가 그 값을 엔진에 다시 넣어야 하고, 블루프린트에 보이는 값과 실제 값이 달라집니다. JSON은 기획자가 AI를 시켜 값만 고쳐 바로 플레이해 보는 곳이라, 기획서에 있는 값만 둡니다. |
| 묶는 단위 | 캐릭터마다 JSON 하나와 DataAsset 하나(`Player.json`과 `DA_Player`, `Boss.json`과 `DA_Boss`)를 두고, 모든 캐릭터에 공통인 규칙은 `CombatRules.json`에, 락온 카메라와 셰이크의 상황별 단계는 `Camera.json`에 둡니다. 셰이크 단계별 값은 카메라 셰이크 에셋 3개에, 이펙트는 GameplayCue 에셋에, 공격 예고 섬광이 켜지는 구간은 보스 패턴 몽타주의 노티파이에, 화면의 크기·배치·표시 시간은 위젯에, 글자 크기 단계는 CommonUI 글자 스타일에 둡니다. | 한 캐릭터의 수치를 파일 하나에서 모두 볼 수 있습니다. |
| JSON 파일 | 프로젝트 폴더의 `Data`에 둡니다. 키는 C++ 필드 이름 그대로 쓰고, 모든 필드를 빠짐없이 적습니다. 패턴 ID 같은 게임플레이 태그는 태그 이름으로, 열거형은 값 이름으로 적습니다. MP·UP 충전은 플레이어 공격에만 있고, 그 밖의 공격 데이터는 플레이어와 보스가 같은 필드를 씁니다. 그 캐릭터가 쓰지 않는 필드(보스 공격의 PP 배율, 플레이어 공격의 가드·패리 가능, 플레이어의 PP)도 기본값으로 적습니다. | `Content`에 두면 에디터가 JSON을 에셋으로 가져오려 합니다. 기획서, 데이터 위치표, 코드, JSON의 이름이 같아 대조하기 쉽습니다. 쓰지 않는 필드 몇 개 때문에 구조체를 나누지 않습니다. |
| 읽는 방법 | JSON은 프로젝트의 에셋 매니저(`UAgAssetManager`)가 읽습니다. 캐릭터 DataAsset은 로드될 때 에셋 매니저에 자기 JSON(`ValuesFile`)을 넘겨 같은 객체의 Transient 필드를 채웁니다. 공통 JSON은 에셋 매니저가 엔진 초기화 때(`StartInitialLoading`) 자기가 가진 공통 데이터 객체(`UAgCombatRules`, `UAgCameraData` 하나씩)에 읽고, 코드는 이 객체를 에셋 매니저에서 받아 씁니다. 대상 찾기 프리셋(`TP_Enemy`)은 `DA_Player`가 가리킵니다. | 에셋 매니저는 게임 전체가 쓰는 데이터를 엔진 초기화 때 읽도록 엔진이 열어 둔 확장 지점이고(Lyra 샘플도 게임 데이터를 여기서 읽습니다), 에디터·쿡·패키징 빌드에 모두 있습니다. 엔진이 GC 제외 객체 풀을 닫은 뒤에 만들어 엔진 객체의 UPROPERTY로 들고 있으므로, 에셋 매니저가 UPROPERTY로 든 공통 데이터 객체도 GC가 따라갑니다('객체 수명'). 값을 쓰는 코드는 값이 어느 파일에서 왔는지 몰라도 됩니다. 게임 중에는 파일을 읽지 않습니다. |
| 오류 검사 | 읽을 때 문법, 모르는 키, 빠진 키, 값의 형식, 없는 태그·열거형 값, 정수 필드의 소수를 검사하고, 에디터에서는 필드의 허용 범위(배열 원소는 배열 필드의 범위)도 검사합니다. 키는 대소문자를 구분하지 않습니다. 오류가 있으면 그 파일의 값을 하나도 바꾸지 않고 로그와 화면에 띄웁니다. | 엔진의 JSON 변환기는 모르는 키를 무시하고 빠진 키도 다 잡지 못해, 오타가 조용히 기본값이 됩니다. 엔진의 이름(FName)과 JSON 객체도 키의 대소문자를 구분하지 않고, 패키징 빌드의 필드 이름은 대소문자를 보존하지 않습니다(예: `UP`이 `Up`으로 나옴). |
| 다시 읽기 | 에디터는 `Data` 폴더를 지켜보다가 JSON이 저장되면 그 파일을 다시 읽습니다. 쓸 때마다 읽는 값(리젠 회복량, HUD의 보스 이름 포함)은 다음 동작부터 바뀌고, 스폰할 때 넣는 값인 스탯은 PIE를 다시 시작해야 바뀝니다. DataAsset과 프로젝트 설정의 값은 에디터에서 고치면, 쓸 때마다 읽는 값은 바로 바뀌고 스폰할 때 넣는 값은 다음 PIE부터 바뀝니다. DataAsset 편집을 실행 취소하거나 다시 실행하면 그 DataAsset의 JSON을 다시 읽습니다. 패키징 빌드는 시작할 때 한 번만 읽습니다. 데이터 배열의 원소(패턴, 타격 데이터)를 가리키는 포인터나 참조는 그 함수 안에서만 쓰고, 나중에 쓸 값은 복사해 두거나 키(패턴 ID, 타 번호)로 다시 찾습니다. | 컴파일 없이 PIE 중에 수치를 바꿔 볼 수 있습니다. 스탯을 다시 넣으면 HP가 처음 값으로 돌아가 싸움이 초기화됩니다. 다시 읽으면 배열의 원소를 새로 만들고 원소 수가 바뀌면 배열이 다른 메모리로 옮겨지므로, 원소를 가리킨 채 다음 프레임까지 들고 있으면 해제된 메모리를 읽어 에디터가 크래시합니다. |
| 패키징 | `Data`의 JSON은 빌드 규칙(`RuntimeDependencies`)으로 pak에 넣습니다. | `Content` 밖의 파일은 쿡이 모릅니다. |
| 데이터를 찾는 방법 | 공통 JSON은 에셋 매니저가 정한 파일 이름(`CombatRules.json`, `Camera.json`)으로 읽고, 캐릭터 DataAsset은 캐릭터 블루프린트에서 가리킵니다. 캐릭터 블루프린트에는 데이터만 넣고 이벤트 그래프는 쓰지 않습니다. 캐릭터 DataAsset은 필수라, 캐릭터가 시작할 때 한 번 확인하고(없으면 멈춤) 그 밖의 코드는 있다고 보고 씁니다. | 코드에 에셋 경로를 쓰지 않습니다. 공통 JSON 파일은 그 파일을 읽는 클래스와 짝이라 이름을 바꿀 일이 없습니다. |
| 어빌리티의 데이터 | 어빌리티는 C++ 클래스만 두고, 몽타주와 수치는 캐릭터 데이터의 해당 항목(예: 평타 1타)에서 읽습니다. | 캐릭터의 데이터가 JSON 하나와 DataAsset 하나에 모입니다. |

### 애니메이션과 이동

| 항목 | 결정 | 이유 |
| - | - | - |
| ABP | `ABP_Ag` 하나를 플레이어와 보스가 같이 씁니다. 값은 C++ `UAgAnimInstance`에서 계산하고, 애님 그래프에는 이동 블렌드 스페이스 → 가드 이동 블렌드 스페이스 전환 → 공중 여부 전환 → 몽타주 슬롯 → 덧입힘 슬롯만 둡니다. 두 전환의 블렌드 시간은 노드 핀에 적고, 공중 전환은 노드의 엔진 기본값(0.1초)을 그대로 씁니다. 루트 모션은 몽타주에서만 씁니다. | AI가 BP 그래프를 다루기 어려우므로 그래프를 최소로 둡니다. 블렌드 시간은 노드의 설정이라 노드에서 고칩니다('데이터'의 '형식'). |
| 블렌드 스페이스 | 플레이어 이동(템플릿 `BS_Idle_Walk_Run`: MM_Idle, Walk·Jog 8방향), 플레이어 가드 이동(Guard, Guard_Walk 8방향), 보스 이동(Idle1, Walk 8방향) 3개를 캐릭터 데이터에 넣어 바꿔 끼웁니다. 가로축은 캐릭터 정면 기준 이동 방향, 세로축은 이동 속도이고, 샘플은 각 모션의 실제 이동 속도에 둡니다. 팩의 이동 모션은 제자리(`_IPC`) 버전을, 템플릿 이동 모션은 루트 모션을 켠 원본(재생할 때 제자리)을 씁니다. | 세 블렌드 스페이스의 축이 같아 ABP 하나로 처리됩니다. 템플릿 블렌드 스페이스는 샘플이 모션의 실제 속도(걷기 3m/s, 뛰기 6m/s)에 있어 그대로 씁니다. |
| 메시 갱신 | 캐릭터 메시는 화면에 보이지 않을 때도 포즈와 본을 갱신합니다. | 공격 판정이 메시의 피직스 바디를 쓰고 무기가 손을 따라가므로, 보이지 않을 때도 위치가 맞아야 합니다. |

| 슬롯 흐림, 쿨다운 표시 | 슬롯 흐림은 스킬·궁극기 어빌리티의 비용 확인을 그대로 불러 정합니다. 쿨다운 표시는 어빌리티의 쿨다운 GameplayEffect에서 남은 시간과 전체 시간을 읽어, 숫자는 위젯에 쓰고 원형 표시 머티리얼에는 남은 비율만 넘깁니다. 둘 다 흐려지는 슬롯 위젯 바깥에 둡니다. | 사용 조건과 쿨다운을 어빌리티 한 곳에만 둡니다. 덮는 모양은 머티리얼이 정합니다. |
| 그로기 중 PP 바 | 보스가 그로기 시간을 세기 시작한 시각(공중에서 그로기가 되면 착지한 때)을 기록하고, HUD는 지난 시간을 그로기 지속 시간으로 나눈 만큼 채웁니다. PP 바의 감소 잔상도 이 채운 값을 따라갑니다. | 그로기 시간과 같은 기준으로 채웁니다. |
| 월드 위치 HUD | 락온 마커, 처형 안내, 대미지 숫자는 화면 공간 위젯 컴포넌트로 표시합니다. 락온 마커와 처형 안내는 보스의 락온 지점과 머리 본에 붙이고, 보스가 매 프레임 표시 여부를 정합니다. 대미지 숫자는 대미지 GameplayEffect가 실행하는 큐(`GC_DamageNumber`)가 플레이어가 준 대미지일 때 맞은 위치에 액터를 생성하고, 액터가 떠오르는 동안 투명해지는 것은 위젯 애니메이션이 맡습니다. 표시 시간(애니메이션 길이)과 떠오르는 높이는 위젯에 둡니다. 대미지 숫자는 실제 시간으로 흘러 슬로우모션의 영향을 받지 않습니다. 상황별 표시 규칙은 HUD와 이 위젯들이 각각 따릅니다. | 대미지 숫자는 HUD가 숨은 뒤에도 끝까지 재생해야 해 HUD와 따로 둡니다. 위젯 애니메이션은 실제 시간으로 재생되므로, 떠오르는 것도 실제 시간으로 세면 둘을 맞추려고 게임 속도를 넘길 필요가 없습니다. |
| UP 게이지 | 텍스처 없는 기능용 UI 머티리얼로 슬롯 테두리를 채웁니다. 채우는 모양은 머티리얼이 정하고, 코드는 UP 비율만 머티리얼 파라미터로 넘깁니다. 채우는 수식은 머티리얼의 Custom 노드(HLSL) 하나에 넣어 그래프를 작게 둡니다. | 코드가 아트를 직접 그리지 않고 모양은 에셋이 맡습니다. 수식이 텍스트라 AI도 고칠 수 있습니다. |
| 화면 UI | 타이틀과 결과 UI는 CommonUI 화면으로 만듭니다. 화면마다 입력 모드(화면 UI는 UI 전용 입력과 커서 표시, HUD는 게임 입력과 커서 숨김)와 첫 선택 버튼을 정합니다. 화면의 버튼은 모두 공용 버튼 `WBP_AgButton`을 쓰고, 상태별 모양과 효과음은 표준 버튼 스타일 `ButtonStyle_Ag`가 정합니다. 효과음은 스타일의 `Hovered Sound`와 `Clicked Sound`를 쓰며, 재생은 Slate 버튼이 맡으므로 코드는 없습니다. 버튼은 포커스를 받으면 선택되고 포커스를 잃으면 선택이 풀리므로, 선택된 모양은 포커스를 가진 버튼 하나에만 남습니다. 마우스를 올리면 포커스를 가져옵니다. ↑·↓ 이동은 Slate의 기본 내비게이션입니다. 실행 키(좌클릭, Enter, Space)는 Slate 버튼의 기본 처리로 동작하므로 CommonUI 입력 데이터(확인·뒤로 액션)는 만들지 않고, CommonUI 설정 `CommonButtonAcceptKeyHandling`을 `TriggerClick`으로 둡니다. 결과 UI가 화면을 어둡게 하며 나타나는 페이드 인은 위젯 애니메이션(`FadeInAnimation`)이 맡고, 코드는 그것을 재생하고 끝나면 버튼을 켭니다. | 새 화면의 버튼도 같은 모양이 되도록 모양을 한 에셋에서 관리합니다. `Pressed Sound`는 누르는 순간 재생되어, 누른 채 버튼 밖으로 끌어내 실행을 취소해도 소리가 납니다. 스타일 사운드는 마우스 호버와 버튼 입력에 재생되고, ↑·↓로 포커스를 옮길 때는 재생되지 않습니다. Lyra 샘플처럼 포커스 이동에 소리를 내는 코드는 두지 않습니다(게임패드 이동은 CommonUI가 커서를 포커스된 버튼으로 옮기므로 호버음이 납니다). 페이드의 길이와 모양은 대미지 숫자처럼 위젯에서 바꿉니다. CommonUI의 `SetIsSelected(false)`는 토글 버튼만 선택을 풀어 주므로, 선택 해제는 `ClearSelection`으로 합니다. CommonUI 입력 데이터는 입력 아이콘 표시와 뒤로 가기 처리에만 쓰이는데, 기획서에는 둘 다 없습니다. 이 설정의 기본값(`Ignore`)은 Enter와 Space를 버튼에 넘기지 않습니다. |
| 게임 모드 | 레벨마다 하나씩, 타이틀용과 보스전용을 `AAgGameMode`를 상속해 둡니다. | |
| 결과 처리 | 보스전 게임 모드가 플레이어와 보스의 사망 가운데 먼저 처리된 것으로 결과(보스는 Stage Clear, 플레이어는 Game Over)를 정하고, 사망 연출 시간이 지나면 결과 UI를 띄웁니다. 그 밖의 캐릭터가 사망해도 결과와 HUD는 바뀌지 않습니다. Try Again은 레벨을 다시 로드합니다. | 게임 플로우의 Stage Clear와 Game Over는 보스와 플레이어의 사망으로만 정해집니다. |

### 개발 도구와 검증

| 항목 | 결정 | 이유 |
| - | - | - |
| 테스트용 콘솔 명령 | 개발 빌드에만 둡니다. 보스·플레이어를 사망시키는 명령(`AgKillBoss`, `AgKillPlayer`)입니다. 그 밖의 상황(그로기, 자원, 무적)은 PIE 중 에디터 파이썬으로 만듭니다('에디터 파이썬 원격 실행'). | 단계별 확인과 QA에서 결과 UI를 빠르게 확인합니다. 플레이어에게 보이는 기능이 아닌 개발 도구입니다. |
| PIE 확인용 입력 | 플레이어 캐릭터에 에디터 전용 속성(`DevPressInput`, `DevMashInput`, `DevHoldInput`, `DevMoveInput`)을 둡니다. PIE 중 에디터 도구로 값을 넣으면 키를 누른 것과 같이 처리합니다. | AI가 키보드 없이 PIE에서 행동을 확인합니다. 에디터 빌드에만 있어 게임에는 들어가지 않습니다. |
| 프로젝트 MCP 도구 | 엔진 MCP 도구와 에디터 파이썬으로 바꿀 수 없는 설정(몽타주 섹션, 몽타주 구간과 구간별 재생 속도, 슬롯 그룹, 위젯 애니메이션, 블루프린트 컴포넌트의 Parent Socket, StateTree 에셋의 생성과 상태·태스크·전환 편집과 컴파일)을 바꾸는 도구를 에디터 전용 모듈 `AgEditor`의 `UAgAssetToolset`에 둡니다. 엔진 MCP에 툴셋으로 등록해, AI가 열린 에디터에서 다른 MCP 도구처럼 부릅니다. 엔진 도구로 할 수 있는 일은 이 툴셋에 두지 않습니다. StateTree 에셋을 읽을 때는 엔진의 StateTree 조회 도구를 쓰고, 스키마의 속성은 엔진의 `set_properties`로 스키마 객체에 씁니다. | 몽타주처럼 반복되는 에셋 작업을 AI가 처리합니다. ('위험 요소'의 에디터 작업량) 엔진에 들어 있는 MCP 도구에는 이 기능이 없습니다. 엔진의 StateTree MCP 도구는 조회만 하고, StateTree 편집 함수는 C++ 에디터 API에만 있습니다. 게임 모듈에는 게임 코드만 둡니다. |
| 에디터 파이썬 원격 실행 | Python 플러그인(에디터 전용)과 원격 실행(`DefaultEngine.ini`)을 켭니다. AI가 열린 에디터에서 파이썬으로 에셋을 고치고, PIE 중에 테스트용 콘솔 명령을 실행합니다. 원격 실행은 엔진 기본 설정대로 이 PC 안에서만 열립니다. | 에셋 작업마다 에디터를 닫고 헤드리스로 처리하지 않아도 되고, 에디터 도구(MCP)로 읽거나 바꿀 수 없는 값(몽타주 노티파이, 배열 등)도 다룰 수 있습니다. |
| PIE 마우스 포커스 | 에디터 플레이 설정 'Game Gets Mouse Control'을 켭니다(`DefaultEditorPerProjectUserSettings.ini`). PIE가 시작하면 게임 뷰포트가 포커스를 가져가고, 보스 스테이지에서는 마우스를 바로 잡습니다(Shift+F1로 풀림). | 꺼져 있으면 PIE가 뷰포트 포커스 없이 시작하는데, CommonUI는 에디터에서만 이때 화면의 입력 설정(커서, 마우스 캡처)과 첫 포커스를 건너뛰고 다시 적용하지 않습니다. 그러면 타이틀에서 빈 곳을 클릭할 때 뷰포트가 마우스를 잡아 커서가 사라집니다. 에디터 설정이라 패키지 게임에는 영향이 없습니다. |
| [데이터 위치표](<데이터 위치표.md>) | 데이터 필드(JSON, DataAsset)를 코드로 만들 때마다 행을 추가하고, 코드 리뷰 때 표와 대조합니다. | 실제 필드 이름과 항상 맞습니다. |

## 확인 기록

단계 완료 확인에서 기록하기로 한 결과입니다. 수치를 고칠지는 QA에서 판단합니다.

| 단계 | 확인 항목 | 결과 |
| - | - | - |
| 3 | 평타 1타가 정지 간격에서 맞는지 | 대기 중인 보스에게는 1 ~ 5타가 모두 맞습니다. 멀리서 다가가 정지 간격에서 멈춘 경우와 정지 간격 안쪽에서 바로 친 경우 모두 맞았습니다. 보스가 패턴(B1, A1)을 쓰는 중에는 보스 자세와 움직임에 따라 빗나가기도 했습니다(평타를 14초 동안 연타했을 때 1타와 5타는 모두 맞고, 2 ~ 4타는 19번 중 5번 빗나감). |
| 4 | 스킬의 타가 정지 간격에서 맞는지 | 대기 중인 보스에게 스킬이 정지 간격에서 맞았습니다. |
| 4 | 처형 두 모션의 정렬 | 처형 피격이 처형의 첫 베기에 맞춰 시작하도록 고친 뒤(폴리싱 26), 두 몽타주의 재생 위치가 매 프레임 같았습니다. 보스 정면 2.5m, 측면 60° 2.9m, 0.75m 거리, 평타 직후 어디서 시작해도 첫 베기 순간 두 캡슐 중심 사이가 70cm이고 서로 마주 봅니다. 두 번의 베기와 발차기가 보스에게 닿고, 마지막 일격의 칼은 칼을 뽑아 보스가 날아갈 때까지 몸에 꽂혀 있습니다. 처형으로 사망하면 첫 베기든 마지막 일격이든 처형 사망 모션으로 자세가 튀지 않고 이어진 뒤 래그돌이 됩니다. |
