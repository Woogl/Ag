# 기본 방침

구현 전체에 적용하는 방침을 정합니다.

| 항목 | 결정 | 이유 |
| - | - | - |
| 진행 방식 | 타이틀 화면 → 최소한의 전투가 되는 보스전 → 결과 UI를 먼저 잇고, 그 위에 기능을 채웁니다. | 마일스톤 목표 1을 일찍 확보하고, 늘 처음부터 끝까지 실행되는 상태를 유지합니다. |
| 새 에셋 위치 | 새로 만드는 에셋은 `/Game` 바로 아래 종류별 폴더에 둡니다([에셋 목록](<에셋 목록.md>)). 템플릿 에셋은 원래 폴더(`Characters/Mannequins`, `LevelPrototyping`, `Variant_*`)에, Fab 에셋은 `Fab`에 둡니다. | 경로에 프로젝트 이름(`/Game/Ag`)이나 같은 단어(`/Game/Game`)가 겹치면 헷갈립니다. 템플릿·Fab 에셋은 각자의 폴더에 있어 구분됩니다. |
| Fab 모션 | 쓰는 시퀀스의 루트 모션 설정은 원본에서 켭니다. | 같은 모션을 두 벌 두지 않습니다. |
| 템플릿 코드·콘텐츠 | 새 코드는 Ag 접두사로 따로 만듭니다. LV_BossStage를 Lvl_Combat에서 복사한 뒤, 템플릿 코드(`Variant_*`, `AgCharacter`)와 템플릿 블루프린트(애니메이션·위젯 블루프린트 포함), 샘플 레벨 4개, 입력·AI 에셋을 지웁니다. 메시, 머티리얼, 텍스처, 애니메이션, 몽타주, 나이아가라, 컨트롤 릭 같은 리소스는 대역 에셋(NS_Damage, LevelPrototyping 폴더) 말고도 나중에 쓸 수 있어 남겨 둡니다. 패키징은 게임 맵 2개(`LV_FrontEnd`, `LV_BossStage`)만 쿡합니다. | LV_BossStage를 만들기 전에는 Lvl_Combat이 템플릿 에셋을 쓰므로 지울 수 없고, 그 뒤에는 비슷한 이름의 템플릿 클래스가 혼동을 줍니다. 템플릿 블루프린트와 그에 딸린 레벨·입력·AI 에셋은 템플릿 캐릭터용이라 쓰지 않고, 상당수는 부모 클래스(템플릿 코드)가 없어 쓸 수도 없습니다. 쿡할 맵을 정하지 않으면 프로젝트의 모든 맵을 쿡합니다. |
| 시간 처리 | 기획서의 시간 규칙이 애매하면(타이머와 모션 시간, 게임 시간과 실제 시간 등) 구현하기 쉬운 쪽으로 정하고 구현 계획서에 적습니다. | 기획 단계에서 정한 방침입니다. |
| 구조 선택 | 코드 구조는 AI가 작업하기 편한 쪽보다 엔진이 권장하는 쪽을 따릅니다. 엔진·프레임워크 기능이 기대대로 동작하지 않으면, 관계없는 클래스(PlayerController 등)에 우회 코드를 넣지 않고 그 기능의 설정과 확장 지점(에디터 설정, 위젯, CommonUI 하위 클래스 등)을 먼저 찾습니다. 예외로, 몽타주 안에서 게임 규칙이 쓰는 시각은 엔진 노티파이 대신 프로젝트 코드가 몽타주 시간표로 판정합니다([몽타주 시간표](<몽타주 시간표.md>)). | 엔진 기능을 설계된 대로 써야 코드가 엔진의 동작과 어긋나지 않습니다. |
| 객체 수명 | `TStrongObjectPtr`와 `AddToRoot`를 쓰지 않습니다. 객체는 그것을 쓰는 액터나 컴포넌트가, 게임 전체가 쓰는 객체는 에셋 매니저가 UPROPERTY로 들고, 네이티브 클래스의 기본 객체(프로젝트 설정 포함)에는 값(수치, 열거형, 소프트 경로)만 둡니다. | 객체 수명을 GC가 관리합니다. 패키징 빌드에서는 네이티브 기본 객체를 GC가 따라가지 않으므로, 나중에 만들거나 읽은 객체를 가리키게 두면 안 됩니다. |
