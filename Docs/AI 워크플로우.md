# AI 워크플로우

기획자와 프로그래머가 각자 AI를 쓰며 효율적으로 일하기 위한 규칙입니다.

## 책임

사람은 방향을 정하고 승인하며, AI는 기획서·데이터·에셋·코드 작업을 수행합니다. 결과는 지시한 사람이 확인하고 책임집니다.

| 담당자 | 책임 |
| - | - |
| 기획자 | 기획서 최신화, 수치 밸런싱 방향, 결과의 기획 의도 충족 여부 |
| 프로그래머 | 기획에 따른 구현, 코드 유지 보수, 빌드·실행 가능 상태 유지 |

## 진행 순서

요청받은 작업부터 독립적으로 시작하고 그 범위까지 수행합니다. 필요한 기존 기획서·데이터·코드를 확인하고, 문서 동기화는 아래 '협업 규칙'을 따릅니다. 범위 밖 후속 작업은 결과 보고에서 알립니다.

### 기획 작업

기획자가 방향을 정하면 AI가 기획서·데이터·근거를 제안하고, 연관 기획서의 영향·충돌과 현재 마일스톤 범위를 점검합니다. 사람이 검토해 확정할 때까지 수정하며, 기획서 수정으로 완료합니다.

### 데이터 작업

기획자 또는 프로그래머의 직접 요청이나 후속 요청으로 시작합니다.

1. 해당 기획서와 수정할 데이터를 확인합니다. 데이터 위치를 모르면 [데이터 위치표](<Program/데이터 위치표.md>)에서 찾습니다.
2. 기존 데이터로 조정할 수 있으면 기획서에 변경을 반영한 뒤 데이터를 수정하고, 둘의 일치를 점검합니다.
3. 사람이 확인하면 완료합니다. 추가 조정은 같은 순서로 진행합니다. 규칙 변경·구현이 필요하면 필요한 기획 변경과 구현 요청을 정리해 사람에게 알리고 종료합니다.

### 구현 작업

1. 요청과 기획서를 확인합니다. 기획이 불명확하면 사람의 답을 받아 기획서를 수정·확정합니다.
2. 구현 문서를 작성·갱신하고 프로그래머의 설계 승인을 받습니다. 수정 요청이 있으면 문서에 반영해 다시 검토받습니다.
3. 승인된 설계에 따라 코드·데이터·에셋과 관련 문서를 반영하고 빌드·동작을 검증합니다. 동작 테스트는 아래 '테스트 작업'을 따릅니다.
4. 사람이 코드와 결과를 확인하면 완료하며, 수정 요청이 있으면 반영·검증을 반복합니다.

### 테스트 작업

기획자 또는 프로그래머가 요청한 정상 동작과 관련 경계·예외 상황의 시나리오를 준비합니다. 통과 조건은 기획서와 기술 규칙에 근거합니다.

테스트 창, PIE, 패키지 게임을 띄우기 직전에 무엇을, 창 몇 개로, 얼마나 확인할지 사람에게 묻고 답을 받은 뒤 시작합니다. 사람이 직접 플레이해 확인하는 편이 나을 때가 있기 때문이며, 작업 계획을 승인받은 것은 이 물음을 대신하지 않습니다. 테스트 때문에 `Data` JSON을 고쳐야 하면(예: 로더의 오류 검사) 먼저 묻습니다. 테스트 방식은 [개발 도구와 검증](<Program/개발 도구와 검증.md>)의 '동작 테스트 실행', 실행 방법은 [시나리오 테스트 README](<../Scripts/ScenarioTest/README.md>)를 따릅니다. 시나리오 조정을 요청받으면 수정한 뒤 실행 여부를 다시 확인합니다.

테스트가 끝나면 결과와 로그를 확인하고 창을 닫습니다. 결과 보고 전에 이번 테스트에서 추가한 임시 코드·시나리오 파일을 정리하고 임시로 바꾼 설정을 복원하며, 공용 테스트 도구(`Scripts/ScenarioTest`)는 유지합니다. 실행을 취소하거나 테스트가 실패해도 같은 정리를 합니다.

완료 후 통과·테스트 실패·실행 실패와 판정·로그 근거를 대화로 보고합니다. 실행을 취소했다면 정리 후 미실행으로 보고하고 종료합니다.

## 협업 규칙

- 기획서
  - 기획서에 적지 않은 기능은 만들지 않습니다.
  - 기획서를 수정하면 변경 내용과 연관된 기획서도 점검하고, 함께 바뀌어야 하는 내용은 반영합니다.
  - 사람이 확정한 답이나 변경 요청으로 기획이 바뀌면, 데이터·코드를 수정하기 전에 기획서에 반영합니다.
- 데이터
  - 데이터는 기획서에 적은 수치(스탯, HP 배율), 설정값(가드 가능 여부), 에셋(모션, VFX)을 말합니다.
  - 기획 데이터와 UE 에셋의 관리 기준은 [AGENTS.md](<../AGENTS.md>)의 코딩 규칙을 따릅니다.
  - 데이터를 바꾸면 기획서도 함께 고칩니다.
  - 각 데이터가 어느 파일(JSON 데이터 파일, 에셋)에 들어 있는지는 [데이터 위치표](<Program/데이터 위치표.md>)에 정리합니다.
  - 기획자는 데이터 작업으로 게임을 조정합니다. 규칙을 바꾸는 변경은 프로그래머에게 요청합니다.
- 구현
  - 구현은 기획서 본문을 따릅니다. 첨부 그림은 이해를 돕는 참고용이며, 좌표·크기·색을 그대로 옮기지 않습니다.
  - 게임 로직의 구현 언어, BP 에셋의 사용 범위, 기획 데이터의 단일 원본은 [AGENTS.md](<../AGENTS.md>)의 코딩 규칙을 따릅니다.

## 문서 위치

문서의 역할과 작업별·주제별 진입점은 [문서 인덱스](<인덱스.md>)를 따릅니다.

## 문서 작성 규칙

- SSoT(Single Source of Truth)를 지킵니다. 수치, 규칙 같은 사실은 그것을 정의하는 문서의 한 곳에만 적고, 다른 곳에서는 '~를 따릅니다', '~ 참고'로 가리킵니다.
  - 용어는 [용어집](<용어집.md>)을 따릅니다.
  - 결정한 내용은 저장소의 문서에 적습니다. 개인 AI의 메모리나 대화는 출처가 될 수 없습니다.
- 문서는 현재 상태만 적습니다. 지난 상태나 변경 경위는 남기지 않고 git 기록에 맡기며, 조사 문서처럼 시점이 중요한 문서에는 갱신일만 적습니다.
- `Docs/Plan`의 설계안과 초안은 완료하거나 확정하면 해당 구현 문서·기획서로 옮기고 원본은 지웁니다. 회의(`Docs/Meeting`)에서 확정한 결정은 해당 정본에 반영합니다.
- 기획서에는 플레이해서 확인할 수 있는 것(규칙, 수치, 화면 배치)을 적습니다. 플레이로 구분할 수 없는 것(코드 구조, 에셋 구성, 엔진 기능 선택)은 구현 문서에서 정합니다.
- 클래스를 더하거나 빼거나, 클래스의 역할이나 클래스 사이의 관계를 바꾸면 그 클래스가 속한 구현 문서의 '클래스 구조'도 함께 고칩니다.
- 기획서에는 현재 마일스톤의 내용만 적습니다. 다음 마일스톤에 대한 언급이나 '나중에 검토' 같은 문구는 쓰지 않습니다.
