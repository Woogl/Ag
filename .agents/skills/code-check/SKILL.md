# 코드 점검

코드를 읽고 실제 문제만 찾아 보고한다. 규칙은 [AGENTS.md](<../../../AGENTS.md>)의 '코딩 규칙'과 구현 계획서(`Docs/Program`)를 따르고, 이 파일은 점검 순서와 판단 기준만 정한다.

## 범위

- 사용자가 정한 범위(전체, 폴더, 바뀐 부분)를 본다. 정하지 않았으면 `Source`에서 git이 추적하는 파일 전체를 본다.
- 사용자가 관점을 정하면(예: 불필요한 코드만) 그 관점만 본다.

## 점검 기준

| 관점 | 보는 것 | 기준 문서 |
| - | - | - |
| 동작 | 기획서와 구현 계획서대로 동작하지 않는 것, 크래시, 객체 수명, 순서와 타이밍, 패키지 빌드에서만 깨지는 것 | 기획서, 구현 계획서 주제 문서, [기본 방침](<../../../Docs/Program/기본 방침.md>) '객체 수명' |
| SSoT | 같은 값·상태·규칙을 두 곳에 두는 것, 데이터를 코드에 직접 쓰는 것 | [AI 워크플로우](<../../../Docs/AI 워크플로우.md>) '협업 규칙', [JSON 데이터](<../../../Docs/Program/JSON 데이터.md>) |
| 불필요한 장치 | 쓰이지 않는 코드, 엔진·프레임워크 기능과 겹치는 직접 구현, 프레임워크를 우회하는 예외 처리 | [기본 방침](<../../../Docs/Program/기본 방침.md>) '구조 선택' |
| 프로젝트 규칙 | AGENTS.md '코딩 규칙'과 주제 문서의 '기술 결정'을 어긴 곳 | AGENTS.md, 구현 계획서 주제 문서 |
| 문서 대조 | 데이터 필드 ↔ 데이터 위치표, 클래스 ↔ 주제 문서의 '클래스 구조' | [개발 도구와 검증](<../../../Docs/Program/개발 도구와 검증.md>) |

## 진행

1. 범위의 파일 목록을 만든다(`git ls-files Source`).
2. 하위 에이전트를 쓸 수 있으면 폴더별(어빌리티, AI, 캐릭터, 전투, 애니메이션, 데이터, 게임·UI, 에디터 모듈)로 나눠 동시에 찾게 한다. 맡길 때 이 파일의 '점검 기준'과 '보고하지 않는 것'을 함께 넘긴다.
3. 찾은 항목은 하나씩 검증한다.
   - 코드를 직접 다시 읽는다.
   - 엔진 동작에 기대는 주장은 엔진 소스(설치된 UE 5.8의 `Engine/Source`, `Engine/Plugins`)로 확인한다.
   - 어떤 상황에서 무엇이 잘못되는지 구체적으로 적을 수 없으면 뺀다.
4. 지난 결정인지 확인한다. 구현 계획서 '기술 결정'에 이유와 함께 적힌 것, 그리고 커밋 이력(`git log -S`, `git log -L`)으로 보아 일부러 바꾼 것은 되돌리자고 하지 않는다. 그 결정 자체에 문제가 있으면 결정을 바꿀지 묻는 질문으로 올린다.

## 보고하지 않는 것

- 캐릭터가 쓰지 않는 필드가 공용 구조체와 JSON에 기본값으로 있는 것([JSON 데이터](<../../../Docs/Program/JSON 데이터.md>) '파일 구성')
- 손맛과 보기의 문제. 기획자가 직접 플레이하며 판단한다([마일스톤1 계획](<../../../Docs/Design/마일스톤1 계획.md>) '핵심 전투 재미 검증').

## 보고와 수정

- 결과는 대화로, 심각한 것부터 보고한다. 보고서 파일은 요청받았을 때만 만든다.
- 항목마다 위치(파일:줄), 무엇이 잘못되는지, 실패하는 상황(어떤 입력이나 상태에서 무엇이 틀리는지), 고치는 방법을 적는다. 문제가 없으면 없다고만 쓴다.
- 고치는 것은 승인을 받은 뒤에 한다. 동작이 기획서와 다르면 기획서와 코드 가운데 어느 쪽을 고칠지 먼저 묻는다.
- 고친 뒤에는 빌드한다(`ag-editor-workflow` 스킬 '빌드와 에디터 재시작'). 함께 고칠 문서는 [개발 도구와 검증](<../../../Docs/Program/개발 도구와 검증.md>)의 '데이터 위치표'와 '클래스 구조' 행을 따른다.
