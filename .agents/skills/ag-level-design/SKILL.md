# 레벨 디자인 작업

> 작성 중(2026-11-15). 레벨디자이너가 계속 고치는 중이며, MCP로 브러시를 만드는 방법 등 일부는 추후 결정이다.

레벨디자이너가 AI와 함께 레벨을 만들 때 지킬 규칙과, 지금까지 밟은 함정을 모았다. 에디터를 켜고 빌드하고 저장하는 공통 요령은 [ag-editor-workflow](<../ag-editor-workflow/SKILL.md>)를 따르고, 이 파일에는 레벨 작업에만 해당하는 것을 적는다.

## 먼저 지킬 것

- 레벨은 레벨디자이너가 에디터에서 직접 고치는 일이 많다. 작업 전에 레벨을 다시 읽어 현재 상태를 확인하고, 내가 모르는 변경이 있으면 되돌리기 전에 묻는다.
- 구조가 바뀌는 제안(벽, 단, 길의 모양)은 말로만 설명하지 않는다. 만들기 전에 위에서 본 그림으로 먼저 보여 주고 승인받는다.
- 장애물 위치 수정 같은 간단한 작업은 원래 상태를 따로 남기지 않아도 된다. 구간을 통째로 갈아엎거나 많은 액터를 지우는 등 중대한 작업이라고 판단되면, 시작 전에 원래 상태(액터 이름, 위치, 크기)를 남겨 둘지 묻는다.

## 구조물 만들기

### 지오메트리 브러시로 만든다

- 레벨에 만드는 모양(바닥, 벽, 단, 경사로, 엄폐물, 장식용 구조물 등)은 모두 지오메트리 브러시로 만든다. 적, 시작 위치, 트리거처럼 이미 있는 액터를 배치하는 것은 해당하지 않는다.
- 브러시 액터의 스케일은 항상 (1, 1, 1)로 둔다.
- 크기를 바꾸고 싶으면 스케일이 아니라 디테일 패널의 브러시 세팅(Brush Settings) 값(X, Y, Z 등)으로만 조절한다.
- 다른 사람이 스케일을 바꿔 둔 브러시를 발견하면 고치기 전에 알린다.
- 이 규칙 이전에 스태틱 메시 큐브로 만든 기존 지형은 그대로 둔다. 새로 만드는 것에만 적용한다.

### AI가 브러시를 만드는 방법

MCP로 만드는 방법은 추후 결정한다(2026-11-15 프로그래머에게 보고, 대기 중). 결정되면 이 절을 고친다. 그 전까지는 에디터 파이썬 원격 실행([ag-editor-workflow](<../ag-editor-workflow/SKILL.md>) '연결')으로 만든다.

지금 엔진 MCP 도구로 확인한 것(2026-11-15):
- `SceneTools.add_to_scene_from_class`로 `Brush`를 만들면 모양이 없는 빈 브러시가 나온다. `brushBuilder`는 `ObjectTools.set_properties`로 붙일 수 없다.
- 이미 있는 브러시의 빌더(예: `...Brush_1.CubeBuilder_0`)의 `x`, `y`, `z`는 `ObjectTools.set_properties`로 바뀌고 테두리도 바뀐다. 하지만 보이는 형상은 형상 다시 빌드(`MAP REBUILD`) 전까지 옛 크기로 남는다. MCP에는 이 명령을 실행하는 도구가 없다.
- 인터넷에서 BSP 브러시를 만드는 외부 MCP 서버는 찾지 못했다. 가장 가까운 것은 Geometry Script로 메시를 만드는 방식이라 이 규칙에 맞지 않는다.

에디터 파이썬으로 만드는 순서:

1. `unreal.SystemLibrary.execute_console_command(에디터 월드, "BRUSH ADD")`를 부른다. 빌더 브러시(빨간 선 상자)의 위치와 모양 그대로 박스 브러시가 하나 생긴다. 새 액터는 명령 전후의 액터 목록을 비교해 찾는다.
2. 새 브러시의 `brush_builder`(박스면 `CubeBuilder`)에서 `set_editor_property("x" / "y" / "z", 값)`로 크기를 정한다. 값을 넣는 즉시 모양이 다시 만들어진다. 파이썬에는 `Build` 함수가 없으니 부르지 않는다.
3. `set_actor_location`으로 위치를 옮기고 `set_actor_label`로 이름을 붙인다.
4. 다 만들면 `execute_console_command(에디터 월드, "MAP REBUILD")`로 형상을 다시 빌드한다. 이때 볼륨(PostProcessVolume, NavMeshBoundsVolume 등)도 브러시라서 저장 안 된 상태로 표시된다.
5. 위치와 이름은 MCP 도구(`ActorTools`)로 바꿔도 된다. 만드는 단계만 파이썬이 필요하다.

- `BRUSH ADD`로 생긴 액터의 기본 이름은 "박스 브러시"다.
- 브러시 액터는 액터 파일(`__ExternalActors__`)이 아니라 맵 파일(`.umap`) 안에 저장된다. 같은 맵을 다른 사람이 동시에 고치면 맵 파일 충돌이 나기 쉬우니, 맵을 고치기 전에 다른 사람이 작업 중인지 확인한다.
- 원기둥, 계단 같은 다른 모양(`CylinderBuilder` 등)으로 만드는 방법은 아직 확인하지 않았다.

### 재질

- 기본 재질은 `/Engine/EngineMaterials/WorldGridMaterial`(언리얼 기본 회색 격자)이다. 브러시는 따로 지정하지 않아도 이 재질로 나온다.
- 레벨디자이너가 다른 색이나 재질을 요청하면 그것으로 바꾼다. 브러시 면의 재질을 파이썬으로 바꾸는 방법은 아직 확인하지 않았다.

## MCP로 작업할 때 주의할 것

AI가 실제로 실수했던 것들이다. 같은 실수를 되풀이하지 않는다.

- MCP 도구를 쓰려면 에디터가 `-ModelContextProtocolPort=<포트>` 옵션으로 켜져 있어야 한다. 옵션 없이 켜진 에디터는 MCP 연결을 거부한다. 에디터 파이썬 원격 실행은 옵션 없이도 된다. 재시작이 필요하면 먼저 묻는다.
- 새로 만든 액터는 `SceneTools.save_actor`로 저장되지 않는다("Asset does not exist"). `AssetTools.save_assets`에 빈 목록을 줘서 바뀐 것 전부를 저장한다.
- 도구 호출 도우미 함수의 인자 이름을 `name`으로 두지 않는다. 도구 입력값 `name`과 겹쳐 호출이 멈춘다.
- `CaptureViewport`는 `annotations` 값이 필수다. 격자와 이름표를 끄려면 `{"gridSpacing": 0, "gridExtent": 0, "gridHeight": 0, "maxLabelDistance": 0}`을 넣는다. 찍은 이미지는 결과의 `returnValue.image.data`(base64)에 있다.
- 액터를 지우면 빈 폴더는 저절로 사라진다. 그 뒤 `delete_folder`를 부르면 "폴더 없음"으로 실패한다.
- `execute_tool_script` 안의 도구 호출은 하나에 약 0.16~0.18초 걸린다. 액터 200개쯤의 이름을 다 읽으면 20~30초가 든다.

### 지운 액터가 남는 문제

- 적처럼 액터 파일(`Content/__ExternalActors__/Maps/<맵 이름>/...`)로 저장되는 액터는, 지우고 저장해도 파일이 남는 일이 있었다. 에디터를 다시 켜면 지운 것이 다시 나온다(원인은 아직 모른다).
- 지운 뒤에는 `git status`에 해당 액터 파일이 D(삭제)로 뜨는지, 액터 파일 수가 줄었는지 확인한다.
- 같은 이름의 액터가 겹쳐 있는지는 이름만 모아서 비교하면 못 잡는다. 이름과 위치를 같이 비교한다.

## 작업 순서

1. 좌표표를 먼저 만든다. 액터마다 이름, 위치, 크기, 회전을 적고, 만들기 전에 계산으로 겹침과 높이를 검증한다.
2. 좌표표대로 배치하고 저장한다.
3. 레벨을 다시 열어 좌표표와 대조한다.
4. 위에서 본 캡처를 찍어 레벨디자이너에게 보여 준다.
5. 에디터 호출은 기록 파일을 남기며 한다(어떤 도구를 몇 번 불렀는지). 작업 보고서를 요청받을 수 있다.

## 기획서와 그림 맞추기

- 레벨 기획서는 `Docs/Design/Level/`, 배치·높이 그림은 `Docs/Art/Level/`에 있다.
- 기획서에는 플레이해서 확인할 수 있는 것(공간, 높이, 적 배치, 수치)만 적는다. 액터 이름, 엔진 기능, 코드 흐름은 적지 않는다([AI 워크플로우](<../../../Docs/AI 워크플로우.md>)).
- 레벨디자이너가 에디터에서 직접 고친 뒤에는 레벨을 읽어 실제 좌표로 기획서와 그림을 다시 맞춘다.

## 플레이 확인

- 계산이나 선 검사(시야 검사)가 통과해도 "사수가 쏜다", "적이 길을 찾는다"고 말하지 않는다. 실제 플레이로 확인하기 전까지는 "계산상"이라고 밝힌다.
- 원거리 적처럼 전투 AI가 필요한 확인은 `LV_SimulationRoom`을 `?Enemies=` 옵션으로 열어서 한다(예: `?Enemies=,,Gunner,,`). 콘솔 `summon`으로 부른 적은 플레이어를 보지 못한다.

## 레벨 설계 기본

- Ag는 패리·가드 공방과 스킬 콤보 중심의 액션 게임이다(명말, 인왕 느낌). 레벨과 적 배치를 제안할 때 공방과 패리로 풀 수 있는 구조를 우선한다.
- 레벨마다의 설계 규칙(장애물 쓰임, 구간 구성, 원거리 적 위치 등)은 해당 레벨 기획서(`Docs/Design/Level/`)를 따른다. 한 레벨에서 받은 피드백을 다른 레벨에 그대로 옮기지 않는다.

## git

- 브랜치는 만들기 전에 레벨디자이너에게 묻는다.
- 에디터의 Git 연동은 새로 저장한 액터 파일을 자동으로 스테이징한다. 커밋 전에 스테이징된 파일이 이번 작업 것인지 확인한다.
- 병합 충돌이 나면 팀원 작업을 우선한다. 그리고 어떤 파일이 왜 충돌했고 어떻게 처리했는지(누구의 무엇을 살리고 무엇이 빠졌는지) 레벨디자이너에게 보고한다.
