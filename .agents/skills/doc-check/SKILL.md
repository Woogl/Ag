# 문서 점검

문서끼리, 그리고 문서와 데이터·코드 사이의 어긋남을 찾아 보고한다. 문서 규칙은 [AI 워크플로우](<../../../Docs/AI 워크플로우.md>)의 '협업 규칙'과 '문서 작성 규칙'을 따르고, 이 파일은 점검 순서와 판단 기준만 정한다.

## 대상

| 대상 | 위치 |
| - | - |
| 기획서 | `Docs/Design`, 첨부 그림 `Docs/Design/Attachments` |
| 용어 | `Docs/용어집.md` |
| 구현 계획서 | `Docs/Program` (주제 문서, 데이터 위치표, 구현 위치표, 에셋 목록) |
| 에셋 조사 | `Docs/Art` (기획서가 '참고'로 가리키는 모션과 측정값) |
| 데이터 | `Data/*.json`, 데이터 위치표가 가리키는 블루프린트·위젯·프로젝트 설정 |
| 코드 | `Source/Ag`, `Source/AgEditor` |
| 모션 그림 정의 | `Scripts/MotionImages/sheets` |
| 스킬 | `.agents/skills` |

사용자가 범위를 정하지 않으면 전부 본다.

## 점검 항목

1. 기획서 ↔ 데이터: 기획서의 수치와 설정이 [데이터 위치표](<../../../Docs/Program/데이터 위치표.md>)가 가리키는 필드의 값과 같은지 본다.
   - JSON은 파일을 읽는다.
   - 에셋 값은 열린 에디터에서 읽는다. 에디터를 쓸 수 없으면 `ag-editor-workflow` 스킬의 '에디터 없이 읽기'를 따른다.
2. 위치표 ↔ 실제: 데이터 위치표, [구현 위치표](<../../../Docs/Program/구현 위치표.md>), [에셋 목록](<../../../Docs/Program/에셋 목록.md>)이 가리키는 필드, 클래스, 에셋이 실제로 있는지 본다. 반대로 코드의 데이터 필드(JSON 키)가 데이터 위치표에서 빠지지 않았는지도 본다.
3. 기획서 규칙 ↔ 코드: 구현 위치표에서 구현 위치를 찾아, 기획서의 규칙(순서, 조건, 시간 기준, 예외)이 코드와 같은지 본다.
4. 구현 계획서 ↔ 코드: 주제 문서의 '기술 결정'과 '클래스 구조'(클래스, 부모, 역할, 관계)가 코드와 같은지 본다.
5. 문서 ↔ 문서:
   - [AI 워크플로우](<../../../Docs/AI 워크플로우.md>) '문서 작성 규칙'(SSoT, 용어집, 기획서에 적는 범위)을 어긴 곳
   - 없는 문서나 절을 가리키는 링크와 참조, 없는 첨부 그림, 어디서도 쓰지 않는 첨부 그림
   - 모션 그림 정의의 표시(타이밍, 문구)가 기획서와 다른 곳
6. 스킬 ↔ 문서: 스킬이 문서의 규칙이나 결정을 다시 적었거나 문서와 다르게 적은 곳, 없는 절을 가리키는 곳. 스킬에 무엇을 적는지는 [AI 워크플로우](<../../../Docs/AI 워크플로우.md>) '문서 위치'의 `.agents/skills`를 따른다.

## 진행

1. `git status`와 `git log`로 지금 상태를 보고, 최근 커밋이 바꾼 문서부터 확인한다.
2. 하위 에이전트를 쓸 수 있으면 영역을 나눠 동시에 맡긴다. 맡길 때 이 파일의 '판단 기준'을 함께 넘긴다. 나누는 예는 다음과 같다.
   - 기획서 ↔ 데이터
   - 플레이어·전투 규칙 ↔ 코드
   - 보스·카메라·HUD·화면 규칙 ↔ 코드
   - 위치표, 문서끼리, 스킬
3. 찾은 항목은 근거 파일을 직접 다시 읽어 확인한다. 확인하지 못한 항목은 보고하지 않는다.
4. 사람이나 다른 AI가 같은 문서를 동시에 고칠 수 있다. 보고하기 직전에, 점검하는 동안 바뀐 파일(`git status`, 수정 시각)을 다시 읽는다.

## 판단 기준

- 실제 문제만 보고한다. 문서가 스스로 모순되는 것, 문서와 데이터·코드가 다른 것, 적힌 대로 만들면 눈에 띄게 깨지는 것, 지난 변경을 덜 고친 흔적이 여기에 든다.
- 다음은 보고하지 않는다.
  - 엔진 기본 동작이 정하거나 구현자가 정할 수 있는 엣지 케이스, 1초도 안 되는 드문 타이밍 겹침
  - 손맛과 보기의 문제. 기획자가 직접 플레이하며 판단한다([마일스톤1 계획](<../../../Docs/Design/마일스톤1 계획.md>) '핵심 전투 재미 검증').
  - 캐릭터가 쓰지 않는 필드가 공용 구조체와 JSON에 기본값으로 남아 있는 것([JSON 데이터](<../../../Docs/Program/JSON 데이터.md>) '파일 구성')
- 어느 쪽이 맞는지는 커밋 이력으로 판단한다. `git log -S'<값이나 이름>'`이나 `git log -L`로 두 쪽이 언제 바뀌었는지 찾는다. 한쪽만 최근에 일부러 바뀌었으면 다른 쪽을 덜 고친 것이다. 그래도 판단이 서지 않으면 묻는다.
- 용어집의 영문 표기와 코드의 이름이 다르면 [용어집](<../../../Docs/용어집.md>) '사용 규칙'을 따라 고칠 쪽을 정해 보고한다.
- 규칙의 문구에는 걸려도 규칙의 목적에 어긋나지 않는 쓰임은 보고하지 않는다. 그런 쓰임이 많으면 규칙의 문구를 좁히자고 제안한다.

## 보고와 수정

- 결과는 대화로 보고한다. 보고서 파일은 요청받았을 때만 만든다.
- 항목마다 위치(파일과 절이나 줄), 무엇이 어긋나는지, 어느 쪽이 맞아 보이는지와 그 근거, 고치는 방법을 적는다. 문제가 없으면 없다고만 쓴다.
- 고치는 것은 승인을 받은 뒤에 한다. 고치는 순서는 [AI 워크플로우](<../../../Docs/AI 워크플로우.md>) '협업 규칙'을 따른다.
